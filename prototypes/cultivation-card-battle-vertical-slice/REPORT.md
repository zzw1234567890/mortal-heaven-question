## 验证问题 (Validation Question)

> 一个从零开始的玩家，是否能在 4 分钟内无需开发者引导地体验到「炼气战斗 → 修为满 → 渡劫 → 突破筑基 → 再战」的核心循环 —— 并且我们能否在 1 周内以具有代表性的质量构建出这样一个循环？

**答案：玩家能独立完成完整循环，2 分钟到达首次有意义操作。UI 简陋导致修仙幻想传递失败。构建可行但需要 UI 投入大幅增加。**

## 建议 (Recommendation)：继续 (PROCEED)

完整的 [开始 → 挑战 → 解决] 循环已在 Godot 4.6 GDScript 中以零编译错误实现并通过试玩验证。验证问题中的可行性部分已确认：玩家可以独立完成炼气战斗→修为满→渡劫→突破→再战的完整循环。构建速度数据表明，以当前代码架构，完整战斗系统的实现是高效的（4 天完成 16 个文件的约 3000 行代码）。

**但验证问题中的体验部分 —— "修仙突破的爽感" —— 未通过。** 这是预期的：纯程序化 UI 无美术资产、无音频、无动画，无法传递情感张力。这不构成 PIVOT 或 KILL 的理由；它确认了生产阶段需要在 UI/UX 和视听呈现上投入显著更多资源。

## 生产要求 (Production Requirements)

**必须改变的内容：**
1. **UI 资产化** — 程序化 UI 仅适合原型；生产需要 `.tscn` 场景 + 美术素材 + 图标
2. **音频系统** — 零音频使得所有反馈缺失；需要卡牌打出音效、命中音效、渡劫氛围音
3. **动画系统** — 卡牌打出、伤害数字弹出、角色受击闪烁
4. **渡劫过场** — 当前简单闪烁效果太弱；需要更震撼的视觉呈现
5. **美术风格定义** — 当前无统一视觉风格，仅靠颜色区分

**需要的架构调整：**
- 生产环境中需将垂直切片系统映射到 Foundation 层 ADR（GSM、EventSystem、CombatSystem 等）
- `battle_hud.gd` (671 行) 和 `enemy_ai.gd` (329 行) 超过 300 行限制，生产拆分

**基于切片数据的冲刺速度估算：**
- 每个卡牌效果类型：0.5 天（伤害/治疗/护盾/绑定/灵力/前排/AOE）
- 每个敌方类型 + 行为序列：0.5 天
- 每个 UI 界面（选择/战斗/奖励）：1 天（生产质量）
- 完整战斗循环系统：~5 天

**对原始设计的范围调整：**
- 13 张卡牌构成可靠的基础卡池——生产可扩展至 30+
- 6 角色 × 6 阵位模型验证通过——阵法系统可在此基础上叠加
- 境界压制公式在切片中运作良好——无需返工

**性能目标**：已确认 — 纯 2D UI 在 RTX 3050 上零性能压力，生产阶段需在低端 GPU 上验证。

## 经验教训 (Lessons Learned)

- **Godot 4.6 GDScript inline if/else 限制**：`if cond: stmt() else: stmt2()` 单行语法不被支持，必须展开为多行 `if`/`else` 块。这在 Godot 4.6 文档中没有明确说明，是 LLM 训练数据（Godot ≤4.3）与实际引擎版本的差异点。

- **inline `:=` 类型推断失败**：`var d := dict[key].duplicate()` 当 `dict` 是 typed `Dictionary` 时，GDScript 无法推断 `duplicate()` 的返回类型，需要使用显式类型注解 `var d: Dictionary = ...`。

- **程序化 UI 的一个致命限制 —— 数据/UI 状态同步**：按钮的 `disabled` 状态在跨场次时不会自动重置。`VSDeploymentState.remove_character()` 清除了数据层，但 UI 层按钮的 `disabled` 状态残留，导致第二场战斗的绑定/治疗/护盾目标选择不可用。这暴露出垂直切片中数据层和 UI 层之间的同步缺陷 —— 生产环境中应由信号驱动的自动刷新机制覆盖。

- **如果再运行一次**：
  1. 首日就拆分 `battle_controller.gd` —— 588 行巨大文件导致大量 Python3 脚本修复产生损坏
  2. 提前制定 UI 状态同步契约 —— 每个数据变更的信号必须对应 UI 刷新方法
  3. 试玩测试应更早进行 —— D4 就应做首次试玩，而非等到 D7
