## 技术发现

| 发现 | 详情 |
|------|------|
| **UI 程序化布局耗时** | Godot 的 Control 节点在父节点为普通 Node 时 anchors 不可靠——多次手动调整 offset_left/offset_right 居中 |
| **`_ready()` 时序** | `add_child()` 后 `_ready()` 在下一帧才执行——`set_rewards()` 前需 `await process_frame` |
| **`get_node_or_null()` 失败** | `queue_free()` 调用后原脚本实例可能已被释放——成员变量直接追踪比查找路径可靠 |
| **25 Autoload 未被验证** | 切片只用了 3 个节点（PlayerState/EnemyAI/Deployment）——生产环境的 25 Autoload 初始化顺序仍待测试 |
| **双焦点未被触及** | 切片中无键盘导航——60fps 稳定，但双焦点合规性未被测试 |
| **架构遵循** | const 数据表 + 委托模式 + snake_case 信号均按控制清单执行 |

## 经验教训

1. **程序化 UI 不适合游戏 HUD**——`.tscn` 场景文件提供了可视化的 WYSIWYG 编辑器，代码布局的调试成本远超预期。生产实现中所有战斗 UI 应使用 `.tscn` + `@onready` 引用。

2. **`await process_frame` 是 Godot 的"下一帧"惯用法**——`add_child()` 后立即操作子节点属性的标准模式。

3. **切片范围纪律有效**——砍掉探索/阵法/炼丹让 D1 就能穿线完整循环。6 个系统而非 15 个。

4. **修为曲线需拆分调参**——一场战斗 40-80 修为 vs 100 上限导致突破太密。切片中 max_cultivation 应 > 单场奖励的 3 倍以确保至少 2-3 场才触发。

5. **创意总监 CONCERN 1：修为曲线压缩**——一场战斗即突破消解了支柱 2「步步为营」的核心体验。缓解：修为上限 300 且奖励 20-40，确保 ≥3 场战斗触发突破。

6. **创意总监 CONCERN 2：渡劫战缺失**——突破为零风险按钮点击，削弱了渡劫的仪式感和挑战性。缓解：D2-D4 必须实现渡劫战，含失败损失 10% 修为。

7. **创意总监 CONCERN 3：挣扎感缺席**——全程顺风顺水，没有"差点输了"的紧张时刻。缓解：调参炼气期敌人 + 渡劫战的挑战性，让玩家感受到"被压制"和突破的代价。
